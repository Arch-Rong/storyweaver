# StoryWeaver Agent 开发规范

这份文档面向项目成员和参与开发的 Agent。根目录的 [`AGENTS.md`](../AGENTS.md) 是每次任务的简明规则；本文件补充技能选择、开发流程和验收要求。

## 1. 适用范围

StoryWeaver 是面向作者的小说协作 Agent。项目支持规划、续写、局部改稿、版本管理、一致性检查和定稿后的记忆更新。作者始终拥有是否采纳文本和事实的决定权。

技术基线：前端使用 pnpm、Turborepo、TypeScript、Next.js App Router、React 和 Tiptap；后端使用 Python、uv、FastAPI、Pydantic、SQLAlchemy、Alembic、Celery、PostgreSQL 和 Redis。除非方案文档或任务明确改变，不要引入新的编排框架、缓存、队列或向量数据库。

## 2. Agent 技能配置

### 2.1 项目专用技能

项目技能位于 [`skills/storyweaver-development/SKILL.md`](../skills/storyweaver-development/SKILL.md)。它规定小说领域的核心不变量：

- 正文版本不可变。
- 工作稿、定稿、未来规划、AI 提案和候选记忆分开保存。
- Agent 默认只读，写入先生成提案。
- 采纳时校验版本、段落哈希、权限和 `canonEpoch`。
- 任务可重试、可取消、可恢复，并且不会重复应用副作用。

如果团队把技能安装到个人 Codex 技能目录，保持技能文件内容与项目版本同步；项目规则仍以仓库内的 `AGENTS.md` 为准。Python API 和 Worker 应共用同一后端领域模块，Redis 只做 Celery 调度，PostgreSQL 是任务和正文状态的权威来源。

### 2.2 常用全局技能

| 技能                             | 触发时机                                      | 交付前关注点                                 |

### 2.3 技术资料查询

涉及库、框架、SDK、API 或 CLI 时，优先用 Context7 获取匹配版本的文档；没有可调用的 Context7 时使用官方文档。记录实际采用的版本和 API 约束，不根据记忆猜测接口。

## 3. 小说领域开发规范

### 3.1 状态与事实

正文至少区分工作版本和定稿版本；历史版本不可变。自动保存创建工作版本，作者采纳创建新工作版本，定稿确认才移动定稿指针。

未来规划不能当作已经发生的事实。模型推测不能当作世界真相。人物“知道什么”需要与场景时间和来源版本绑定；角色误解和不可靠叙述不能直接覆盖作者设定。

修改正式章节后，来源版本失效的摘要、事实候选和检索资料要排除在新任务上下文之外。恢复旧正文也创建新版本，并重新走定稿流程。

### 3.2 Agent 工具

工具按只读与提案分组：

- 只读：读取章节、搜索故事、读取人物状态、读取大纲。
- 提案：规划提案、续写提案、正文修改、一致性问题、候选记忆。
- 作者 API：采纳、拒绝、定稿和恢复。

工具必须校验作品归属，结果带来源版本和块 ID，输出经过 schema 校验。Agent 不接收任意路径、任意作品 ID、任意 HTML 或未授权的工具参数。

### 3.3 上下文组装

按以下优先级组装上下文：作者请求和约束、目标版本与选区、硬性设定、章节目标与视角、相关证据原文、摘要和未来规划。明确标注每段资料是“正式事实”“当前草稿”“未来计划”还是“模型提案”。

超出预算时优先保留硬约束、目标段落和证据；不要为了塞入更多资料而丢弃来源标记。记录本次任务实际使用的资料，便于复现和解释。

## 4. 工程开发规范

### 4.1 服务端与数据

- 密钥、数据库连接、模型请求和权限校验只在服务端执行。
- 领域规则放在独立模块；React 组件只负责展示和交互。
- 数据库迁移可重复检查，生产数据操作使用事务和明确的 `WHERE` 条件。
- 模型调用和向量化在事务外执行；事务只完成短时间的数据校验和状态写入。
- Celery 队列任务必须保存状态、尝试次数、租约、心跳和幂等键；任务状态不能只保存在 Redis。

### 4.2 编辑器

- Tiptap JSON 是正文权威格式，Markdown/TXT 是导入导出格式。
- 段落或块使用稳定 ID；提案引用基础版本和块 ID。
- 自动保存检测新旧版本，不能无提示覆盖较新内容。
- 差异视图必须显示修改理由、证据和可能受影响的章节。

### 4.3 API 与错误

- 修改正文的请求包含基础版本和幂等键。
- 并发冲突使用可识别的 409 结果，说明需要刷新、重生成还是重试。
- 任务结果、事件和提案都校验作品归属。
- 错误日志包含任务 ID、版本 ID 和阶段；不记录密钥和完整私密正文。

## 5. 标准工作流程

1. 读取根目录 `AGENTS.md`、相关方案章节、目标包配置和相邻实现。
2. 写出要保持的领域不变量，以及受影响的 API、数据和 UI。
3. 先实现类型、schema、版本校验和事务边界，再实现 Worker、API 和 UI。
4. 针对本次变更运行单元测试、集成测试或端到端测试；不要只测试模型能返回文本。
5. 运行适用的 `pnpm lint`、`pnpm check-types`、`pnpm build`、Python lint/typecheck/test 命令，文档变更运行 `pnpm exec prettier --check` 和 `git diff --check`。
6. 报告实际完成内容、验证命令、测试结果和未验证的风险。

## 6. 重点验收清单

### Agent 任务

- [ ] 刷新页面后能恢复任务状态和已产生的提案。
- [ ] 取消、超时、限流、Worker 退出和队列重复投递都有可解释结果。
- [ ] 重试不会重复插入正文或重复更新事实。
- [ ] 使用了正确的作品、版本、章节和人物认知范围。
- [ ] 达到预算时停止并保留已有结果。

### 编辑与定稿

- [ ] 修改显示差异、理由和证据。
- [ ] 基础版本变化后旧提案不能静默应用。
- [ ] 作者可以逐项采纳、拒绝、撤销和恢复。
- [ ] 工作稿不会污染正式事实。
- [ ] 修改前文后旧摘要与检索片段不会进入新上下文。

### 安全与隐私

- [ ] 模型密钥不进入浏览器、Git 或日志。
- [ ] 每个作品、章节、任务和事件都校验当前用户归属。
- [ ] 工具不能访问任意文件或其他作品。
- [ ] 导入、导出和日志处理不泄露未授权正文。

## 7. 不应默认做的事

- 不把整本小说无筛选地放进每次上下文。
- 不把向量相似度当作事实正确性证明。
- 不让 Agent 直接覆盖定稿正文。
- 不为了“先跑起来”跳过版本校验、幂等键、预算和权限边界。
- 不在没有评测样例的情况下声称某个模型最适合中文长篇写作。
